# pga

Rust terminal UI (ratatui, sync `postgres` crate) for browsing and managing PostgreSQL roles, memberships, database/schema/object privileges, default privileges, RLS and role settings, aimed at users who know MySQL. User-facing usage is in [README.md](README.md).

## Code Layout

| Module | Owns |
|---|---|
| `src/main.rs` | CLI args, password prompt, terminal setup, event loop |
| `src/conn.rs` | libpq-style defaults (`PG*` env, socket probe, `~/.pgpass`, `sslmode`), per-database client cache |
| `src/catalog.rs` | every catalog query and its row type |
| `src/wizard.rs` | multi-step flows that build the GRANT / REVOKE / ALTER / CREATE / DROP SQL |
| `src/app.rs` | navigation path (`Level`, `Place`, `Tab`), lists, keys, running confirmed actions |
| `src/detail.rs`, `src/explain.rs`, `src/ui.rs` | detail pane, `?` explain pane, rendering |

## Conventions

- **Writes go through the confirm dialog.** A wizard builds an `Action`; the user sees the exact SQL; `App::execute` runs it in one transaction. No key runs SQL directly.
- **Identifiers:** quote with `catalog::quote_ident` (keyword list from `pg_get_keywords`). Never interpolate a raw name.
- **Version gates** read `Server.version_num`: `>= 160000` for per-membership `INHERIT` / `SET` / `ADMIN`, `>= 170000` for `MAINTAIN`. Keep the pre-16 fallbacks.
- **Passwords** go out as a SCRAM verifier built client side (`wizard::scram_literal`), never as plain text.
- **Explain notes** (`src/explain.rs`) teach: PG term first, MySQL analogue second. Check wording against the PG docs.

## Verifying Changes

- `cargo clippy --all-targets` clean and `cargo test` green.
- `cargo clippy` does not rebuild `target/debug/pga`. Run `cargo build` before driving the binary.
- **UI:** drive the binary in tmux and read the screen; kill the server after.
  - `tmux -S target/tmux.sock new-session -d -s pga -x 200 -y 40 "target/debug/pga -d <db>"`
  - `tmux -S target/tmux.sock send-keys -t pga 2` (send `Enter` as its own `send-keys`, not with `-l`)
  - `tmux -S target/tmux.sock capture-pane -p -t pga`
- **SQL:** run new write statements in `psql` inside `BEGIN ... ROLLBACK` first. Under the prat sandbox `initdb` cannot start a scratch cluster (SysV shared memory is blocked), so the only server is the local shared one: no real writes from the TUI there.

## Releasing

- **Not on crates.io.** The name `pga` belongs to another crate, so `Cargo.toml` sets `publish = false` and `[package.metadata.dist] dist = true` (dist skips unpublished packages otherwise). There is no crates.io workflow.
- **cargo-dist 0.31** builds releases: `dist-workspace.toml` sets targets, the shell + Homebrew installers and the tap. `.github/workflows/release.yml` is generated by `dist generate`; never hand-edit it, rerun `dist generate` after changing dist config. `dist plan` lists the artifacts a tag would produce.
- **Cutting a release:** `cargo release <patch|minor|major> --execute --no-confirm` bumps `Cargo.toml` and `Cargo.lock`, commits, tags `vX.Y.Z` and pushes `main` and the tag (`[package.metadata.release]` limits it to `main`). cargo-release is not installed on this machine; the manual equivalent is bump `version`, `cargo build`, commit, `git tag vX.Y.Z`, push `main` and the tag.
- **A tag push publishes.** `release.yml` builds the three targets, creates the GitHub Release with `pga-installer.sh`, and pushes `pga.rb` to `bilal-bhatti/homebrew-taps`. Only on explicit instruction.
- **One-time setup:** repo secret `HOMEBREW_TAP_TOKEN`, a PAT with write access to `bilal-bhatti/homebrew-taps`. `GITHUB_TOKEN` is automatic.
- **Versioning:** pre-1.0. The bump level is the maintainer's call; ask.

## Doc System

Doc work is governed by the shared `_contract` and the per-operation procedures (`doc-add`, `doc-update`, `doc-audit`, `doc-split`, `doc-remove`), all rendered by `cura prompt <name>` and injected into the `/doc-*` slash commands in `.claude/commands/`. The slash commands are the formal entry points; the rules apply equally to natural-language doc requests. To read the contract or a procedure directly, run `cura prompt _contract` (or any name). Map by intent, not syntax:

| User intent signal | Procedure to apply |
|---|---|
| "add to X", "update X with Y", "spec says Z now" | `doc-update` |
| "write a spec for X", "plan for Y", "ADR for Z" | `doc-add` |
| "we don't need X", "X is superseded by Y" | `doc-remove` |
| "X is too long", "split off section Y" | `doc-split` |
| "are the docs consistent?", "what's stale?" | `doc-audit` |
| "let's explore X" (no doc named) | Check for an authoritative home; extend (`doc-update`) if one exists, otherwise create (`doc-add`). Never invent a second home for an owned topic. |

Always-on contract pieces (apply whether or not a command was explicitly invoked):

- Every governed-doc edit checks `authoritative-for` first; if out of scope, redirect to the owner doc.
- Every fact is either owned by this doc (declared in its `authoritative-for`) or linked to its owner - never restated.
- Every change enumerates cross-references and propagates explicitly; never silently retarget or delete.
- Every LLM-derived doc populates `derived-from` with the actual sources read.
- Every edit stamps `last-reviewed`.
- Every doc declares a `type` - `Reference | Plan | Overview | Index`, and no other value. It is required and it blocks: a doc created without one fails the commit gate, and a doc touched without one gains one before it lands.
- Soft cap (400 lines) is a flag; hard cap (800 lines) is a stop.
- Refuse to bypass the authority rule "just for now." That's how rot starts.

## Governed Scope

Governed docs live under `docs/`. The full scope table and front-matter schema are in `_contract` §1; run `cura prompt _contract` to read them. The `cura` tool enforces the contract: `cura audit` for health checks, `cura check` for individual checks, and the `.cura/hooks/` hooks gate commits: `pre-commit` on structural defects, `commit-msg` on content this change drops without declaring a `Dropped:` trailer (`_contract` §6.8).

Some of the record lives in commit messages rather than in a doc, because intent is the one thing a diff cannot show: `Dropped:` (this loss was deliberate), `Propagated-from:` (this edit absorbed that source's change), `Demoted-to:` (this doc is no longer the source of truth for that referent). The rule governing them is in `_contract` §5; `cura trailers --keys` prints the three and what each claims, and `cura trailers [--since <ref>]` prints what this repo has actually declared.
